# 图色口径文档 —— 坐标、区域与几何常量怎么定出来的

> 这份文档记录的是**实测统计出来的口径**，不是拍脑袋估的：每一条都注明了样本量与分位数。
> 想换分辨率、换 UI 皮肤、换赛季，必须先按本文方法重新测一遍，再改 `recognize/regions.py` 与 `config/config.py`。

## 0. 两条铁律

1. **一切坐标以 1920×1080 为基准**。游戏窗口捕获后先 `capture.screen.resize(img)` 等比缩放到基准（`LANCZOS`），
   识别区域常量是按这个尺寸标定的；不缩放直接识别，区域全部错位。
2. **格位（cell）是棋盘坐标系的原点**。棋盘 8 行 × 7 列，`recognize/grid.py::board_position(point)` 把任意点映射到
   最近的格位，`bench_position(point)` 映射到备战席 9 格。血条、装备栏、棋子框的位置全部用「相对格心」的偏移表达，
   这样棋盘缩放/平移时不用重标。

## 1. 棋盘与备战席的格心

| 项 | 值 | 来源 |
| --- | --- | --- |
| 棋盘行数 | 8 | `config.BOARD_GRID_ROWS` |
| 棋盘列数 | 7 | `config.BOARD_COLUMNS` |
| 格心 | `grid.board_position()` 由 4 个角点线性插值 | `config` 里棋盘四角坐标（按 UI 皮肤标定） |
| 备战席格数 | 9 | `config.BENCH_SLOT_CENTERS`（13 处引用，是最常改的键之一） |
| 血条→格位的纵向基准 | `BOARD_BAR_TO_CELL_Y`（9 处引用） | — |

### 1.1 格位标签口径（用户 m01029，与源项目 `utils/unit_cell.py` 同源）

内部几何一律用**绝对行 1..8**（从对面前排数到自己底排），但**给人看/给人输**的标签换成半场口径：

| 区域 | 标签 | 说明 |
| --- | --- | --- |
| 我方棋盘 | `r1c1` … `r4c7` | `r1` = **自己最底那排**（绝对行 8），往上数到 `r4`（绝对行 5） |
| 敌方棋盘 | `-r1c1` … `-r4c7` | **负号表示对面**，`-r1` = 对面最靠中线那排（绝对行 4），`-r4` = 对面最远排（绝对行 1） |
| 备战席 | `slot1` … `slot9` | 自左向右 |

实现（`recognize/grid.py`，移植自源项目而非另造）：

- `cell_label(row, column, area="board")`：绝对行 → 人读标签；`parse_cell_label(text)`：标签 → `(区域, 绝对行, 列)`；
- `board_cell_center(row, column)` / `bench_slot_center(slot)` / `resolve_center(spec)`：**格位 → 坐标**的
  唯一实现（源项目 `operations/units.py` 同口径），`label_to_center("r3c4")` 一步到位；
- `scripts/game.py` 的 `cell` / `--row/--col` 都吃这套标签：`r3c4`、`slot5`、`board,r2c3` 三种写法等价，
  带负号的敌方格位**直接报错**（只用于展示，不能放子/点击）。

> 历史坑：内存通道曾把敌方 `-r2c4` 当己方 `own_row=2`，凭空多算一个棋子与一个人口
> （源项目 `mem_provider.py:231` 注释）——所以负号必须在**解析时**就换算成绝对行，不能在中途混用两套量纲。

## 2. 血条（health bar）—— 恒定高 8px

血条是整条识别链里**最稳的锚点**：颜色纯（己方绿/敌方红/中立灰）、尺寸恒定、位置只随格心平移。

| 相对格心的偏移 | 中位 | p10 | p90 | 说明 |
| --- | --- | --- | --- | --- |
| `bar_top − cell_y` | **−105** | −146 | −86 | 血条上沿 |
| `bar_bottom − cell_y` | **−97** | — | — | 血条下沿 |
| 血条高 | **8**（恒定） | — | — | p90 − p10 只有几像素抖动 |

实现口径（`recognize/board.py`）：

- `BAR_REGIONS` 定义每个格位附近的搜索带；模板 `templates/health_bar.png` 匹配，`BAR_MATCH_THRESHOLD=0.65`，
  `BAR_NMS_DIST=50`（同一条血条去重的最小间距）。
- 星级（1★/2★/3★）优先读**血条左侧星级徽记的颜色**（`star_badge()`，见 2.1），读不到才退回数血条条纹
  （`bar_stars()`）；战斗帧备战席单位没有血条，星级显示为 `-`。
- 单位框：`PORTRAIT_H=92`、`PORTRAIT_HALF_W=52`（头像框半宽/高）。
- 图色框的中位：上沿 `格心−88`、高 128、下沿 `格心+40`。**8283 个框里有 3949 个（47.7%）上沿落在装备栏带
  （`格心−90 … −52`）内**，也就是近一半的框把血条+装备栏一起框了进去 → 绘制/裁图时要把上沿**钳到 `格心−49`**。

> 历史教训：血条路径曾用「模板匹配 + 全棋子库头像匹配」定位单位身份，耗时 1.66s/帧且准确率只有 67%；
> 现改为 `extract_units(img, include_legend=True, match_cells=set())` 跳过身份匹配（51ms/帧），**身份交给 YOLO**。

### 2.1 星级徽记 —— 血条定位的锚点（2026-11-14 用户口径）

用户口径（原话）：「血条现在经常定位错误，我们可以结合血条左边必定有[星级]来辅助定位」＋
「我们的hero血条，左边就一定是代表等级的数字」。

也就是说：**血条左边一定挂了徽记，棋子挂星级 chevron、小小英雄挂等级数字**——这个图标是 UI 元素，
比"绿色长条"稳定得多，可以当作血条定位的**正样本锚点**：

| 判据 | 结论 |
| --- | --- |
| 左窗里有彩色 chevron（1★铜 / 2★银蓝 / 3★金） | 一定是**棋子血条**，星级直接读徽记颜色 |
| 左窗里是**白色数字**（框内白像素 ≥25） | 一定是**小小英雄**，星级为 `None`（不是棋子） |
| 左窗里什么都没有 | 这根"血条"是误检 → 丢弃（`BAR_REQUIRE_BADGE=True`） |

实测几何（`recognize/board.py::star_badge`，相对血条 `(x1,y1,x2,y2)`）：

| 量 | 实测 | 常量 |
| --- | --- | --- |
| 徽记搜索窗 | `x1−40 … x1+2`、`y1−12 … y2+12` | `BADGE_WIN=(-40,-12,2,12)` |
| 彩色 chevron 面积 | 1★ 48~128，2★ 193~215px | `BADGE_AREA_RANGE_BY_STARS={1:(40,165),2:(150,280),3:(60,500)}`；另加 `BADGE_ASPECT_RANGE=(0.45,1.8)` 排扁条 |
| 徽记尺寸 | 8×12 ~ 23×26（随单位远近/遮挡） | `BADGE_H_RANGE=(8,30)`、`BADGE_W_RANGE=(6,32)` |
| 竖向对齐 | 徽记中心 vs 血条中心 dy 0~6 | `BADGE_DY_MAX=12` |
| 距血条左沿 | 徽记右边界 = `x1` −5 ~ −17 | 搜索窗内判定 |
| 白像素 | 等级数字框 **52~73**；chevron **0** | `BADGE_NUMBER_WHITE=25` |

颜色区间（OpenCV H 0-179，`BADGE_COLORS`）：

| 档 | 区间 | 实机实测 |
| --- | --- | --- |
| 3★ 金 | `(26,140,110)-(42,255,255)` | 3★ 乐芙兰徽记框 **H=39 / S=158 / V=156**（2026-11-14 实机帧验证） |
| 2★ 银蓝 | `(85,20,120)-(118,120,255)` | H 中位 104~105、S 85~98 |
| 1★ 铜 | `(8,90,110)-(25,255,255)` | H 中位 15~16、S 126~144 |

> 一枚 3★ 徽记框只有 26×14，靠“金区间 + 面积 + 竖向对齐”三重合起来才唯一；
> 单独看色相会和某些装备高光混淆，所以不要放宽面积下限。

> [!] 用用户给的 3 张模板（`templates/star/star_{1,2,3}.png`）直接做 `matchTemplate` 不行：
> 多尺度 `TM_CCOEFF_NORMED` 下 1★ 峰值只有 0.55~0.64、2★ 0.88——模板与实机渲染的尺度/清晰度不匹配。
> 所以模板只作为**口径参照物**留在仓库里，判定走"颜色类 + 几何约束"。
> 要复核/重标定：`python -X utf8 -u tools/probe_star_badge.py --img <帧> --crop`。

### 2.1.2 徽记怎么画出来（`overlay_info` 的星级显示，用户 m01029）

用户原话：「你把星级也用 overlay 显示出来，不然我看不出哪里有问题」。所以 overlay 不只是"画个框"，
而是把**星级的物理来源**摆到眼前：

| 元素 | 画法 | 看什么 |
| --- | --- | --- |
| 徽记框 | 金黄 2px 方框，正好套住血条左侧那枚 chevron | 框没套上 → 血条配错格 / 徽记判据失效 |
| 星级标注 | 并进名字牌前缀：2★/3★ 显示成 `2★ 芸阿娜`，1★ 不显示；徽记框本身只描金框不写字 | 不额外占行——同列行距仅 76px，独立星牌必压上一格（用户 m02211） |
| 等级牌 | 小小英雄的等级数字框 + 「小小英雄 我方/敌方 LvN」牌 | 区分"棋子的星级"与"英雄的等级" |
| 棋子名 | 蓝框下方 `名字 + 置信度`（**不再重复画星**） | 名字与星数在同一列上对齐核 |

数据来源：`board.extract_units` 给每根血条附 `badge_box`（`(x1,y1,x2,y2)`，由 `star_badge()` 的 cv2 口径
`(x,y,w,h)` 换算）与 `stars_source`（`"badge"`＝读徽记 / `"stripes"`＝退回数条纹）；
`overlay/live_draw.py::merge_stars` 把它们按最近中心搬到 YOLO 棋子上，`debug_overlay.draw_frame`
按 `config.OVERLAY_SHOW_STAR_BADGE`（默认 True）绘制。


效果（同一份测试帧，`include_legend=False` 的"棋子血条数"，改动前 → 改动后）：

| 帧 | 血条数 前 → 后 | 说明 |
| --- | --- | --- |
| `board_ingame.png` | 8 → **8** | 一根不少；星级 1/1/2/1/1/1/1/1 与目视一致，小小英雄单独判为 legend（共 9 项里 1 个小英雄） |
| `reward_balls.png` | 7 → **7** | 真对局帧不受影响（含 1 个小英雄，3★ 金徽记在该帧也没有样本） |
| `bench_forge.png`（战斗帧） | 4 → **3** | 丢的是 (1124,84) 那片绿色藤蔓；3 根真战斗血条星级 2★ 正确 |
| `augment_choose.png`（海克斯遮罩帧） | 5 → **1** | 4 根是卡片遮罩上的假条 |
| `board_green_model.png`（非对局帧） | 25 → **0** | 25 根全是假血条，徽记门禁全丢 |

星级也从"数血条条纹"改成**读徽记颜色**——条纹在战斗帧会被分段、被特效压盖时数错，徽记不会。
`bar_stars()` 保留作兜底（徽记没读出来时才用）。

#### 2.1.1 分段血条必须先合回一根（2026-11-14 实测）

战斗/野怪血条是**分段渲染**的（每格之间夹一道深色分隔符），颜色法会沿分隔符把一条血条切成几十片：

- `board_green_model.png` 的野怪大血条被切成 **25 片**，每片都不带徽记 → 被"无徽记即误检"全丢，
  **一根真血条都没留下**（假阴性）。
- 解法：`recognize/board.py::_merge_bar_pieces()` 在血条定位之后、徽记判定之前做合并：
  同一行（`BAR_MERGE_DY=4`）、横向空隙 ≤ `BAR_MERGE_GAP=12` 的碎片并成一根。
  相邻两只棋子的血条横向间距 ≥40px（格宽 78），不会误合并。
- 合并后：`board_green_model.png` 25 片 → 4 行宽条（剩 20 片碎片被丢），对局帧血条数一根不变
  （8/7/3/1 与合并前完全一致）。
- **野怪/多行血条**（绿色大血条 + 下方蓝色护盾条分属不同 y）仍不会被并成一根、也不会带徽记 →
  这在"只认棋子"的用途下按**遗漏**处理（宁可漏，不可误检）。

## 3. 装备栏 —— 恒定高 26px、横向 30px 间距

装备栏紧贴血条下方，是第二条稳定锚点。

| 相对量 | 值 | 说明 |
| --- | --- | --- |
| `equip_top − bar_top` | **+20** | 装备栏上沿 = 血条上沿 + 20 |
| `equip_bottom − bar_top` | **+46** | 装备栏下沿 |
| 装备栏高 | **26**（恒定） | `recognize/equipment.py::BOARD_ICON_SIDE=26` |
| 槽位间距 | **30px** 横排 | 5 槽 |
| 装备栏底 ≈ | `格心 − 51` | 由上面两条推出 |

左侧**装备库存面板**（不是棋子上装备）用另一套口径（`EQUIP_GRID_*`）：

| 键 | 值 | 说明 |
| --- | --- | --- |
| `EQUIP_GRID_ENABLED` | True | 网格法优先 |
| `EQUIP_GRID_TOP_Y` | 119 | 首格 y |
| `EQUIP_GRID_W` / `EQUIP_GRID_H` | 66 / 66 | 单格尺寸 |
| `EQUIP_GRID_PITCH` | 78 | 纵向步进 |
| `EQUIP_GRID_MAX_PER_COL` | 10 | 每列最多 10 个 |

匹配口径：`ICON_THRESHOLD=0.68`（图标灰/彩色匹配下限）；**数量角标**（`x²` 之类）单独走模板匹配，阈值高到 `0.995`
（角标模板差异小，阈值低了会误检）。图标库 = `workspace/scrape_info/v18.3b/images/items/{equipId}.png`（64×64 RGBA），
名称映射 = `config/equip_id_map.json` + `equip_name_map.json`。

## 4. 棋子框（YOLO）—— 宽恒 78

| 项 | 值 | 说明 |
| --- | --- | --- |
| 框宽 | **78**（恒定） | `yolo_v2.1_balls` 与 `yolo_v4.1_units` 系列一致 |
| 框高 | 96 ~ 156（随本体） | 高个子单位更高 |
| 采集侧历史口径 | 78×110 固定 | **与模型输出不一致，是"框对不上"的模型侧根因** |

结论：**不要用采集时的固定高去反推模型框**；下游统一以 YOLO 返回的 `box` 为准，需要裁图时按 `center + 宽高` 现算。

## 5. 奖励球 —— 恒 60×60

| 项 | 值 |
| --- | --- |
| 尺寸 | **60×60** 圆形（蓝 / 银 / 金 三色） |
| 检测方式 | HSV 三色阈值（不训练、不进 YOLO） |
| `BOARD_REGION` | `(250, 150, 1510, 710)` 棋盘搜索区（**y 上界 150**，避开顶部 HUD） |
| `ASPECT_RANGE` | `(0.55, 1.8)` 长宽比过滤 |
| 银球 `V` 上限 `SILVER_V_MAX` | **175**（真样本 V 127~132，界面高光 183~211） |
| 蓝球 `S/V` 下限 `BLUE_S_MIN`/`BLUE_V_MIN` | **175 / 190**（真样本 S 181~204 / V 194~211，小小英雄高光 S 166 / V 181） |
| 颜色名 | `COLOR_NOTES = {blue: 蓝球, silver: 银球, gold: 金球}` |

15 帧实测共 86 个球，形状/色调高度一致 → HSV 足够，**不要为球单独训练 YOLO**（v2.1 确实能吐 `ball` 框，
但父项目识别链路显式丢弃了它，见 `yolo_units.py` 的 `stats["dropped_ball"]`）。

### 5.1 HSV 路的三个顽固误检（2026-11-14 实测，逐候选裁图确认）

用户看叠加图时指出"球有点离谱"，逐候选裁图后发现根因是**三处界面/角色高光被当成球**：

| 误检源 | 位置 | 特征 | 处理 |
| --- | --- | --- | --- |
| 顶部 HUD 物品槽 | x≈1150~1340, y≈40~110 | 低饱和浅色块，被 silver 阈值吃进并拆成 2 个"球" | `BOARD_REGION` y 上界 85→**150** |
| "6人口"按钮高光 | x≈1460~1510, y≈447~498 | 银白箭头，V=191 | `SILVER_V_MAX=175` |
| 小小英雄（企鹅）青色高光 | 棋盘左下 x≈470~500, y≈550~575 | S=166 / V=181 | `BLUE_S_MIN=175` + `BLUE_V_MIN=190` |

验收数据（`tests/images/` 两张真实帧）：

| 帧 | 修复前 | 修复后（真值） |
| --- | --- | --- |
| `board_ingame.png`（准备 3-6，无球） | 4 个（全误检） | **0 个** |
| `reward_balls.png`（捡球帧） | 12 个（含 2 HUD + 1 小小英雄） | **9 个 = 蓝 5 + 银 4**（与逐球目视一致） |

> 取舍：`SILVER_V_MAX` 与 `BLUE_*_MIN` 是"宁可少报也不报界面高光"的方向。若后续帧出现**很亮的银球**被漏，
> 优先放宽 `SILVER_V_MAX`（并按新样本重测），不要退回旧的全量阈值。


## 6. 小小英雄 —— 旧路（白色名牌 / YOLO legend）与 6.1 等级块主路

| 项 | 值 |
| --- | --- |
| 框尺寸 | 约 **123×94**（YOLO `yolo_v2.1_balls` 的 `68 小小英雄` 类，516 个训练框） |
| 二次判据 | 血条上方**白色名牌**存在（`board.py::_has_name_text`） |
| 召回 | **很低**：258 个血条单位里只判出 1 个 |

因此 `board.extract_units(include_legend=True)` 与 YOLO 的 `legend` 框是**两路互补**，不要指望单路全覆盖。

### 6.1 等级块法（2026-11-14 起的主路，用户 m01362 指定）

旧路（白色名牌 + YOLO legend）在战斗帧几乎咬不到，因为**名牌会被特效/血条遮挡**；
改走源项目 `recognize/draft_hero.py` 的口径：**先把等级数字块当锚点，再看它右边一小段是绿还是红**。

| 项 | 值 |
| --- | --- |
| 锚点 | 血条左侧的**等级数字白块**（灰度 ≥230 的连通域，宽 7~24、高 11~28、面积 ≥40） |
| 暗底闸 | 白块外扩 6px 的暗像素（灰度 ≤109）均值 ≥100 —— 挡"亮地形上的白点" |
| 敌我判据 | 数字块右侧 `x+w+4 … x+w+22`、中心行 ±6 的均值 RGB：**绿** = 我方（g>r+50 且 g>b+50 且 g≥110）、**红** = 敌方（r>g+50 且 r>b+40 且 r≥120） |
| 等级 | `recognize/templates/hero_level/{1..10}.png`（16×22 灰度模板）做**余弦相似度**；块整体拉伸到 16×22（不保宽高比，否则窄笔画「1」和「4」会误配 0.80） |
| 落点 | 数字块中心 + `DRAFT_HERO_LEVEL_DX=60.0`、`DRAFT_HERO_LEVEL_DY=54.5` |
| 去重 | 同英雄中心距 < `DRAFT_HERO_LEVEL_TOL=40.0` 合并 |
| 搜索区 | `recognize/hero.py::GAME_REGION=(150,250,1550,820)` —— 躲开顶栏/底栏/右侧玩家列表，否则会多出 2 处假英雄（实测 `enemy Lv6 @(1367,98)`、`enemy Lv1 @(574,947)`） |
| 耗时 | **8~19ms/帧** |
| 实测 | board_ingame `我方 Lv5`（score 0.779，块 (403,502,11,16)）；reward_balls `我方 Lv4`（0.871）；bench_forge `我方 Lv6`（0.889）；augment_choose 0（卡片遮罩帧）；实机 `我方 Lv6`（块 (407,541,11,17)） |

为什么不用 `cv2.matchTemplate` 直接套用户给的 1★/2★/3★ 徽记图：实机按 0.8~1.3 多尺度匹配，
1★ 峰值只有 0.55~0.64、2★ 0.88 —— 模板与实机渲染的尺度/清晰度对不上，当判据会大面积漏报。
徽记图只留作口径参照物（`recognize/templates/star/`）。

**overlay 怎么显示**：等级数字块套**绿框**（我方）/ 红框（敌方），框下方黑底牌写 `小小英雄 我方 Lv5`，
英雄落点再点一个小圈；同一只英雄若同时被 YOLO legend 命中（紫框），紫框会被去重掉（框中心距落点 <70px）。

### 6.2 非对局画面必须整体跳过（2026-11-14 实机踩坑）

在大厅/登录/选英雄/结算这种非对局画面上跑识别，界面美术会被当成目标：实测大厅 K/DA 补给站帧

equip_bar, board_equips, game, augment}`，只有 `phase.detect` 读到 `prep/combat/augment/draft` 才跑这些项，
否则**跳过并把缓存清空**（不保留上一帧脏数据），日志打 `[!] 非对局画面: 跳过 9 项 (...)`。

## 10. 重新标定的方法

换分辨率 / 换皮肤 / 换赛季后按这个顺序做：

1. 抓一帧 1920×1080 基准图（`scripts.game extract --img` 或直接 `capture_game()`）。
2. 用 `python -X utf8 -u tools/selftest_recognize.py --img 新图.png` 看各段是否还能出结果，
   失败段落会指出是模板没命中还是区域没覆盖。
3. 血条/装备栏跑偏时，先打印每根血条相对最近格心的偏移分位数（验收标准：中位仍应在 −105/−97，p10-p90 收窄）。
4. 棋盘格位错位时改 `config` 里四角坐标，而不是改格心；格心由角点插值，改角点最省事。
5. 改完跑 `tools/selfcheck.py --full`，四段自测全绿再提交。

> 验收基准：`tools/selftest_recognize.py` 在 `tests/images/board_ingame.png` 上应得到
> `ocr≈66 条 / YOLO 棋盘 5 + 备战席 3 / 血条 8 / 装备栏 6 件 / 球 0（该帧无球，误检已清） / phase=prep stage=3-6`；
> 数字明显偏离说明口径被改坏了。
