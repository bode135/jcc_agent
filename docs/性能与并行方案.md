| 项 | 值 |
|---|---|
| 文档版本 | **v1.0**（2026-11-19） |
| 对应代码 | `v0.1.x`（`5627eb3` 之后，含头像匹配默认关 / 商店免 det / 价格免 det 三项改动） |
| 状态 | 基准数据已实测；并行方案已定稿，**待实施** |

本文件记录两件事：**当前各识别项的真实耗时**，以及**已设计的并行架构与预期收益**。所有数字都是本机实测，不是推算。

## 六、并行实测（探针）

文件：`tempdir/probe_parallel.py`。两个进程，共享内存预置帧，预热后同时提交；OCR 一路、视觉一路（YOLO + 血条 + hero + 球）。

| 方式 | OCR (ms) | 视觉 (ms) | 墙钟 (ms) |
|---|---|---|---|
| 串行（同进程） | 482.8 | 121.5 | 610.0 |
| 双进程并行 | 519.2 | 121.9 | **563.3** |

- 加速 **1.08x**。
- **OCR 只被拖慢 8%**（482.8 → 519.2），视觉几乎不变（121.5 → 121.9）。

**结论：GPU 争用很轻，并行机制本身可用；但收益取决于两路负载是否均衡。** 视觉轻量项只有 122 ms，单靠它并行只能省 122 ms。真正值得并行的是**装备（961 ms）**。

## 七、并行架构设计

### 7.1 负载分解

| 路 | 内容 | 耗时 (ms) |
|---|---|---|
| OCR 路 | 整帧 OCR 453 + 6 次小区域 OCR ~600（串行） | **~1053** |
| 视觉路 | YOLO 41 + 血条 56 + hero 8 + 球 15 + 装备栏 331 + 携带装备 630 | **~1081** |

两路等长，是并行的理想情形：串行 2134 ms → 并行 max(1053, 1081) ≈ **1100 ms**。

### 7.2 架构

```
主进程                          共享内存 (1920×1080×3, 6.2 MB)
  ├─ 截图 ─────────────────────► [frame shm]
  ├─ 提交任务 ─┐
  │            ├─► Worker-OCR    : ocr.recognize(整帧) + 6 次小区域   (内部串行)
  │            └─► Worker-VISION : yolo + bars + hero + balls + equip + bequip
  └─ 合并结果 ◄──────────────── 两个 Future 都完成后拼成同一份 state
```

### 7.3 关键设计

| 设计点 | 做法 | 理由 |
|---|---|---|
| OCR 不拆 | Worker-OCR 内部保持串行 | OCR 自身已有 6 次小区域，再拆收益低、失败点多 |
| 视觉路内多线程 | `ThreadPoolExecutor(PERF_VISION_THREADS)` | 装备是纯 CPU 的 `cv2.matchTemplate`（630 ms 全在 26×26 ROI 匹配），**cv2 会释放 GIL**，线程有效 |
| 传帧 | `multiprocessing.shared_memory`，只传 shm 名 | 避免每帧 pickle 6.2 MB（~10-20 ms + 内存抖动） |
| 预热 | `ProcessPoolExecutor(initializer=...)` 内加载 ONNX + 空推理 | 冷启动 11~12 s 由常驻进程一次摊掉 |
| 帧一致性 | 写到 shm 后再提交任务，禁止跨帧 | 两条路必须读同一帧 |
| 降级 | 子进程异常或超时 `PERF_PARALLEL_TIMEOUT` → 该帧回落串行 | 不让并行成为新的失败来源 |
| 进程模型 | `spawn`，入口 `if __name__ == "__main__":` | Windows 唯一可用方式 |

### 7.4 三阶段预期

| 阶段 | 改动 | 全量 (ms) | 加速比 |
|---|---|---|---|
| S0 | 现状串行 | 2240.7 | — |
| S1 | 双进程（OCR / 视觉） | ~1170 | 1.9x |
| S2 | 视觉路内部线程池（装备栏 + 携带装备并行，bequip 各 unit 并行） | ~1140 | 2.0x（瓶颈转到 OCR） |
| S3 | OCR 6 次小区域合并成 1~2 次（拼图一次识别） | **~760** | **3.0x** |

核心档 231 ms 不受影响（它本就不含 OCR 那 1050 ms）。

### 7.5 风险

| 项 | 说明 | 应对 |
|---|---|---|
| GPU 争用 | 实测 OCR 慢 8% | 可接受；S3 后 OCR 占比下降，争用更轻 |
| 冷启动 | 11~12 s 一次性 | 只给 overlay 客户端 / `--loop` 常驻场景开；单次 CLI 调用保持串行 |
| 内存 | 每进程 ONNX session 约 200 MB | 2 进程 +400 MB；`PERF_PARALLEL_WORKERS` 可调 |
| 共享内存泄漏 | 异常退出可能残留 | 主进程 `finally` 里 `shm.close()/unlink()` |
| 结果合并 | 两路返回结构不同 | 合并层只做字段填充，不做业务判断 |
